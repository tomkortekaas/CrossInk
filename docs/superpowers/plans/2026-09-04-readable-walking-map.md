# Readable walking map implementation plan

User approved clearer roads/paths, names/landmarks, building outlines, water hatching, larger marker, scale, and approximate direction/distance to route. Codex owns format/embedded integration and acceptance (high risk); no delegation for schema or device writes.

1. Preserve existing v1 overview and SD asset. Add optional detailed file `/Navigation/Maps/detail.walkmap`, used only with a fresh live position; default back to active.walkmap if absent/invalid. Never overwrite the active route or v1 map.
2. X3WM v2 uses the existing 48-byte header/dense CRC directory, 100000 E7 cells, 64-byte records `<iiiiBBBB44s>`: endpoints, kind, flags, text length, zero reserved, printable ASCII text padded with zero. Kinds 1 path, 2 street, 3 main road, 4 building outline, 5 water hatch, 6 water outline, 7 label. Labels have identical endpoints; geometry records have no text. Keep v1 validation strict. Bound v1 to 512MiB and optional v2 to 1536MiB (full province measured at about 1GB; streaming RAM unchanged), each cell 65536 records and visible visit to 200000 records. Stream <=240-byte read buffers and preserve CRC-before-display/fallback.
3. Convert the existing full local PBF with Pyosmium area assembly, preserving polygon holes. Stream records into temporary SQLite (computer only), sort by cell and layer; split geometry at grid boundaries using existing exact splitter. Names are transliterated for the tiny ASCII font. Deduplicate label candidates; produce separate file atomically. Small fixtures check holes, classes, labels and corrupt/truncated payloads before full region conversion.
4. Renderer: narrow streets, dashed paths, bolder main roads, fine building outlines, light water hatching, label halos and bounded collision checks. GPX remains dominant and disconnected segments remain separate. Add a larger marker and a 100m scale for the 400m live viewport. Compute approximate nearest-route direction using existing streamed route geometry, with no routing claim.
5. Verify converter, host reader/render regressions, current Swift off-route behavior, clean navigator target build, and visual preview from real map data. Then copy detail file to user-mounted SD and install verified firmware preserving prior image. User checks GPS, visual clarity, Back, missing-map fallback and outside-route indication.

Off-route investigation: current flag intentionally needs three distinct accepted far fixes; X3 only updates on OK. Do not claim a root cause from one photo. Inspect adapter gating and add visible geometric distance independently of that debounced flag.
